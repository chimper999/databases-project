# Normalization Check with Real-World Data (Assignment 4, Task 4)

This is an update to our week 2 report ([`docs/week2_data_modeling.pdf`](week2_data_modeling.pdf)),
section 8 "Database normalization". In week 2 we normalized the design up to 3NF
using made-up data. Here we check whether the database is still in 3NF now that
it contains the real-world data from `data/SOURCES.md`.

## How we checked

A normal form violation means some column depends on something other than the
whole key. So for every column added or filled by the real data, we asked: *is
this value fully determined by another non-key column?* We tested each possible
dependency on the loaded data with a query like this one, which counts how often
the same value of X comes with more than one value of Y (0 means X → Y holds):

```sql
SELECT COUNT(*) FROM (
    SELECT X FROM SomeTable GROUP BY X HAVING COUNT(DISTINCT Y) > 1
) t;
```

All checks were run on the full database (schema → mock data → real data → CRUD).

## Results

| # | Table | Possible dependency | Result on the data | Violation? |
|---|---|---|---|---|
| 1 | `Affects` | `ExposureScore → ImpactLevel` | Holds for all 1,225 real rows. `ImpactLevel` was computed from the score with a fixed rule (Low < 1/3, Medium < 2/3, High otherwise). | **Yes, 3NF.** Fixed, see below. |
| 2 | `JobPosting` | `Location` is one value | Values mix levels: `"Rome, Metropolitan City of Rome Capital, Italy"`, `"Italy"`, `"Remote"`. 2,693 different values. | **Debatable 1NF.** Documented, not fixed (see below). |
| 3 | `EntryLevelJob` | `OnetSocCode → JobName, JobZone` | Holds | No. `OnetSocCode` is `UNIQUE`, so it is a candidate key, and a dependency on a candidate key is allowed in 3NF. |
| 4 | `JobPosting` | `Location → SalaryCurrency` | 1 location has two currencies | No, not a real dependency. A company can pay in any currency. |
| 5 | `JobPosting` | `JobTitle → EntryLevelJobID` | 22 titles belong to more than one job type | No. |
| 6 | `JobPosting` | `MinSalary = MaxSalary` | True for all 654 real postings with a salary, false for the mock postings | No. The real source only gives one average salary. This is repeated data in the *source*, not a dependency in our design. |
| 7 | `Employer` | Same company stored twice under different spellings | 0 after cleaning (416 spellings merged, see `docs/data_cleaning.md`) | No. |
| 8 | `Employer` | `CompanySize` is `NULL` for all real employers | Missing data | No. A missing value is not a normal form problem, but it is a limitation (see `docs/limitations.md`). |

### Violation 1 (3NF): `ImpactLevel` depended on `ExposureScore`

**Problem.** When we loaded the real data we added `ExposureScore` to `Affects`,
next to the existing `ImpactLevel`. But `ImpactLevel` is calculated from the
score, so the table had a transitive dependency:

```
(AITechnologyID, EntryLevelJobID)  →  ExposureScore  →  ImpactLevel
```

This is exactly the 3NF problem from our week 2 report (there it was
`JobPostingID → EmployerID → CompanyName`). The level was stored twice in
effect: if someone updated a score from 0.30 to 0.70 but forgot the level,
the row would say "Low" with a "High" score, and the database would accept it.

**Fix.** We removed the `ImpactLevel` column and only store the score. The new
view `AffectsWithLevel` (in `sql/02-03_schema.sql`) calculates the level with the
same rule, so it can never go out of sync:

```sql
CREATE VIEW AffectsWithLevel AS
SELECT AITechnologyID, EntryLevelJobID, ExposureScore,
       CASE WHEN ExposureScore * 3 < 1 THEN 'Low'
            WHEN ExposureScore * 3 < 2 THEN 'Medium'
            ELSE 'High' END AS ImpactLevel
FROM Affects;
```

The 15 mock rows only had a level and no score, so we gave them the score in
the middle of their band (Low 0.1667, Medium 0.5000, High 0.8333). Queries 1 and 4
in `sql/06_queries.sql` now read from the view.

**Check.** All 1,225 real rows get the same level from the view as before, and
queries 1 to 4 return exactly the same results as before the change.

### Violation 2 (1NF, debatable): `Location` is not atomic

**Problem.** 1NF asks for one value per cell. In the mock data `Location` was
always a city. The real data puts city, region and country together in one
text (`"Madrid, Spain"`), sometimes only a country (`"Italy"`), and sometimes
`"Remote"`, which is not a place at all. So a question like "how many postings
per country?" can't be answered reliably.

**Why we did not fix it.** Splitting it into `City` and `Country` columns
would need a reliable way to recognise each part, and the formats are too mixed
(1,787 "Remote", 3,941 with only one part, 3,141 with three parts). We record it
as a limitation and as future work: use a source that already has separate
city and country fields.

## Is the real data inserted in normalized form?

Yes. `sql/07_real_data.sql` (generated by `data/clean_transform.py`) never
copies employer or job details into the postings:

1. Each company is inserted **once** into `Employer` (after merging spellings),
   and each occupation once into `EntryLevelJob`.
2. Postings and exposure scores are first loaded into temporary staging tables
   that still contain names and O\*NET codes.
3. `INSERT ... SELECT` with joins then looks up the matching `EmployerID`,
   `EntryLevelJobID` and `AITechnologyID`, so only the foreign keys end up in
   `JobPosting` and `Affects`.
4. The `UNIQUE` and `CHECK` constraints from `docs/data_cleaning.md` stop
   duplicates and impossible values from getting in.

After the fix above, every table is in 3NF again. The only remaining point
is the 1NF note on `Location`, which we accept and list as a limitation.
